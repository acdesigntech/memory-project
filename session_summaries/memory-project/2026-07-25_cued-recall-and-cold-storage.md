## Part 1: Cued/associative recall ("rings a bell")

**The problem it solves**: plain `recall()` only had one confidence cutoff (`RETRIEVAL_FLOOR` on raw strength) — a weak-but-plausibly-related memory either cleared the bar and got treated as a solid hit, or didn't show up at all. There was no middle tier for "this is a stretch, but it might be relevant" the way a real associative memory surfaces weakly-related things without full confidence.

**Design** (`memory_store.py`, refactored `recall()`'s internals into a shared `_score_hits()` helper so both paths use identical scoring):
- **`recall_associative(query, n_results=5, n_activated=3, exclude_topic=None, topic_hint=None)`** returns `{"confident": [...], "activated": [...]}`:
  - `confident` (score >= `CONFIDENT_THRESHOLD` = 0.35, matching `recall_hook.py`'s existing bar): reinforced immediately at the normal rate (`STABILITY_GROWTH` = 1.5x) — identical behavior to plain `recall()`.
  - `activated` (`ACTIVATION_FLOOR` = 0.15 <= score < 0.35): weak, uncertain matches. Deliberately **not** auto-reinforced — surfacing something this way shouldn't count as a real recall until a human confirms it was actually relevant.
- **`confirm_activation(doc_id)`**: called when the user affirms an `activated` hit. Applies `ACTIVATION_STABILITY_BOOST` = 2.5x (bigger than the normal 1.5x) — because a memory retrieved under real uncertainty and then confirmed correct should reinforce *more* than one retrieved easily (the "desirable difficulty" / testing-effect finding from human memory research that the user recalled from the lost 2026-07-17 design session). **No corresponding penalty path on denial** — if the user denies or corrects the guess, the caller does nothing at all; this is explicitly asymmetric by design, not an oversight.
- **Where the judgment call lives**: the function itself doesn't decide what's worth mentioning — it just returns both tiers. Claude is expected to look at `activated`, judge which ones plausibly seem relevant to the actual conversation, and only surface those, using hedging language ("this might be related...", "does this ring a bell...") rather than stating them as fact or dumping every weak match. This is enforced via a global instruction (`~/.claude/CLAUDE.md`), not in code — same pattern as `jot()`'s "call proactively" instruction.
- **Verified**: confirmed `recall()` behaves identically after the refactor (same query, same results). Confirmed `recall_associative()` splits a real corpus query correctly into the two tiers. Confirmed `confirm_activation()` applies exactly 2.5x (tested directly against a real memory's stability field, then restored the memory to its pre-test state afterward so testing didn't leave a permanent artifact in real data).

## Part 2: Cold storage (non-destructive forgetting)

**The problem it solves**: the old `prune()` used `col.delete()` on anything decayed below `DELETION_FLOOR` — permanent, irreversible. The user's objection: that's not how human forgetting actually works. What actually happens is closer to cold storage — inaccessible to ordinary recall, but not truly erased, and a sufficiently specific cue can still resurface it (the "I haven't thought about that in 40 years!" experience). Important clarification from the user mid-design: that resurfacing is typically triggered by something **current** — whatever's live in the conversation right now — not by one stored memory cross-activating another; kept the design to a single current-query lookup rather than any memory-to-memory graph traversal.

**Design**:
- **`prune()` redefined**: instead of deleting, sets `archived=True` + `archived_at` on entries below `DELETION_FLOOR`. Content and embedding stay in `.chromadb` untouched. Idempotent (skips already-archived entries). Still not called from anywhere automatically — has to be run by hand, same as before.
- **`archived` entries are invisible to ordinary retrieval**: `_score_hits()` filters them out unconditionally (same place it filters `exclude_topic`) — they don't show up even in `recall_associative()`'s weak `activated` tier. Cold storage is a harder boundary than "just weakly matched."
- **`recall_cold(query, n_results=3)`**: the only way back in. Searches *exclusively* archived entries, ranked by raw cosine similarity rather than the usual `similarity * strength` (an archived memory's strength is frozen wherever it decayed to and isn't a meaningful ranking signal — it never recovers on its own since `recall()` never touches it again once archived). Filtered against `COLD_REVIVAL_THRESHOLD` = 0.6 — deliberately much stricter than the normal 0.35 confident bar, modeling that resurfacing something long-dormant takes a genuinely specific match, not a loose association.
- **`revive_from_cold(doc_id)`**: called once the user confirms a `recall_cold()` hit is genuinely the thing they meant. Un-archives it and resets `stability` to its own `memory_type`'s base (episodic or semantic, whichever tier it was in when archived — doesn't demote a previously-consolidated memory back to episodic on revival). Ordinary `recall()` finds it again immediately afterward.
- **`purge(doc_id)`**: new, genuinely separate hard-delete escape hatch, for the rare case of something that should never have been recorded at all (e.g. accidentally-jotted sensitive content). Explicitly not routine cleanup — `prune()` is routine cleanup now, `purge()` is not.
- **Verified end-to-end** with a disposable test memory: jotted, artificially aged (forced `last_accessed` back 400 days), confirmed `prune()` archives it (not deletes), confirmed it's invisible to both `recall()` and `recall_associative()`, confirmed `recall_cold()` finds it with a genuinely matching query (0.84 similarity) and correctly does *not* find it with an unrelated query, confirmed `revive_from_cold()` brings it back into ordinary recall, then `purge()`'d it away for real since it was only a test artifact. Also confirmed running `prune()` for real only archived that one disposable entry — nothing in the live corpus was old enough to be swept up.

## Where the criteria for using `recall_cold()` actually stand (discussed after the build)

Not just "try it whenever normal search fails" — the working criteria, in order:
1. Ordinary `recall()`/`recall_associative()` (including the weak `activated` tier) already came up empty — this is a fallback, not a first move.
2. There's a *specific* reason to think something was actually recorded (the user references it in a way implying prior discussion, explicitly asks to check old stuff, or the topic sits in a domain heavily discussed before) — not just a vague feeling it might exist.
3. The query is specific enough to plausibly clear the 0.6 bar — a vague/generic query isn't worth firing this on.
4. It's meant to be occasional, not a routine third-tier fallback for every miss.

**Explicit caveat surfaced when applying these criteria retroactively to the incident that started this session**: `recall_cold()` would *not* have found the original 2026-07-17 associative-recall design notes even if it had existed at the time, because that content was genuinely hard-deleted (file + ChromaDB entry both, per `memory_project_scope.md`'s own note) during the 2026-07-20 pruning — not merely decayed into cold storage. Cold storage only protects things that decay through the archive-based `prune()` going forward; it can't retroactively recover something already truly purged before the feature existed. That specific loss is permanent.
